# Vehicle partnership: usable original-vehicle workspace

This release connects the implemented single-vehicle partnership workflow to the existing vehicle page and financial approval system. It adds a **الشراكة والأرباح** entry in the selected vehicle's profitability report and details page. The direct URL is `/admin/vehicles/<original vehicle ID>?tab=partnership`.

## User workflow

1. Open **تقرير أرباح السيارات**, select the original shared vehicle and click **الشراكة والأرباح**. Only one vehicle can be configured for partnership.
2. Select the two partners from existing AJN customer/supplier/staff records. Enter the legally registered owner, effective date, each original contribution and independent ownership/profit/expense percentages. Each percentage group must total 100%; 50/50 is the initial suggestion. Declared capital is not a receipt. Enter the documented opening loss explicitly, including zero only when correct. Submit the agreement; only the principal administrator approves it.
3. Under **النشاط والمصاريف**, review existing trips and source blockers. Request approval for the real billed external charge or the agreed internal allocation. Internal allocation does not create a second company sale. A no-driver-fee decision is explicit. Existing driver-wage expenses can be submitted as original employee entitlements; a pending original company cash request must be explicitly resolved in its original approval workflow first.
4. Under **الإغلاق الشهري**, choose explicit depreciation/reserve policies and acknowledge the accounting basis. Preview, save a draft, review and submit. Nonzero journals go to the original financial approval screen. A genuinely empty journal has the existing principal-only zero approval. Current months remain provisional. Earlier post-activation months must close in sequence. Blockers show their real causes.
5. Under **المستحقات والتسويات**, review separate categories and canonical paid/remaining/reserved/available amounts. Request a partial/full approved monthly profit or driver payment. Each request links to its exact original MASTER financial detail; principal approval executes it. Pending is not paid, and request/print/view actions never perform an automatic payment.

## Implementation and reused boundaries

- `vehicle-partnership.tsx` reuses AJN controls, TanStack Query, original contacts, exact decimal money and existing authenticated fetch/error UI. Existing terms prefill amendments. A successful save remains successful when a subsequent refresh fails; the refresh issue is reported separately. Mobile layout uses wrapping forms and scrollable data tables.
- `workspace.ts` provides bounded transactional original-source reads and canonical partner/driver balances. Valid missing configuration is explicit; failures propagate instead of appearing empty. Original driver cache reconciliation is transactional and creates no financial record, journal or cash movement.
- `routes.ts` exposes narrow original-source commands through the existing authenticated vehicle API and injected trusted central financial request creator. Preview owns a transaction for its locks. It adds no direct nonzero financial approval endpoint or generic cash/account override.
- The existing MASTER screen gains source labels, exact request-detail links and partnership query invalidation. Its financial approval policy and posting block remain unchanged.
- A real Wouter rendering regression caught query strings being read from pathname-only `useLocation`; the vehicle deep link now uses `useSearch`. A first partial-month regression caught pre-partnership trips/costs blocking closing; readiness now starts at the first effective agreement date, matching financial source evidence, while preserving the original month identity and all approved frozen snapshots. Eligible later and unknown-date sources still block when incomplete.

## Database activation

The already reviewed `lib/db/migrations/0129_vehicle_partnership.sql` was applied alone through the existing `schema:apply` runner after the full release gate passed. It contains no historical backfill or business/financial DML. A read-only owner-connection check first confirmed all nine tables were absent, original prerequisite tables/columns existed and the owner had CREATE/REFERENCES capability. Post-application metadata verification confirmed 9 tables, 124 columns, 80 named constraints, 48 foreign-key targets and 27 named indexes. Constraint-name matching uses the server's actual 63-character identifier limit; no constraint was renamed or dropped. The initial verification detected that naming-normalization mismatch, then the corrected metadata-only verification passed without rerunning the already applied migration. Do not reapply a partial/present schema blindly, run every pending migration or drop objects to roll back. No partner, vehicle configuration, agreement, expense or payment was created during deployment.
