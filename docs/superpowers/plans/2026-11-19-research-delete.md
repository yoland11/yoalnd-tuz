# Research order deletion implementation plan

**Goal:** Add an explicit Arabic delete action to the existing research dashboard, order list, and saved-order workspace.

**Design / implementation choice:** Reuse the existing reversible archive operation (`PATCH /admin/research/orders/:id`) with an additive, explicit `{status:"archived",archiveFromActive:true}` intent. The confirmation identifies the order/student, explains removal from active lists, retained files/history, the student-facing status change and the existing archived filter. Delivered orders or orders with any nonzero canonical price/payment/credit/balance, pending collection, nondeleted expense or active purchase cannot use this delete intent. Permanent database deletion is outside this task.

**Architecture:** One small `ResearchDeleteAction` uses existing AJN AlertDialog, Button, toast, researchFetch and React Query. Permission remains `research.archive`; no new permissions, tables, routes or financial writers. The existing locked update transaction checks canonical payment state and pending holds through the original read helpers, then checks original expenses/purchases. Eligible safe deletion preserves progress, status history, timeline, files and audit. A lost-response retry returns the already archived row without another update/audit. The old status-only archive contract remains unchanged.

**Caller scope:** `ResearchDashboard` and `ResearchOrders` are called only by `research-center.tsx`; propagate an explicit archive grant. `ResearchOrderTable` is also used by research reports: its new grant defaults false so reports remain read-only. Both workspace view and edit mode reuse the one delete action. Existing board/workspace/form PATCH writers gain a shared mutation key so a save disables deletion across both duplicate dashboard views. `updateOrder` is called by the original orders PATCH route; existing edit, assignment, workflow, price and legacy archive callers keep their behavior. No shared payment, approval, cashbox, invoice or financial-report code changes.

**Review focus:** Reader/edit-only users must not gain archive access; cancelled/failed requests must not remove rows; archived financial history remains reachable; no DELETE/storage/payment calls; no stale callbacks or duplicate requests.

**Review rulings:** Existing archive can block subsequent collection and alter delivered-only reporting, so the new intent conservatively excludes delivered/financially committed orders under the original row lock. This avoids changing financial recognition or breaking historical archive callers. Canonical/cost read failures remain structured errors, never eligibility. The progress-preservation regression was observed failing before implementing the safe intent. Independent review found no remaining important/critical issues after the safeguards and mounted-only callback fix.
